# Holdem Tournament Builder

Holdem Tournament Builder — backend для организации домашних офлайн-турниров
по техасскому холдему. Он хранит редактируемые карточки турниров, рассчитывает
стартовые стеки и структуру блайндов, помогает учитывать ребаи и выплаты,
а также формирует расчёты для режима общего банка или переводов между игроками.

Сейчас проект предоставляет HTTP API без frontend. Проект находится в
разработке и не заявлен как production-ready.

## Возможности

- регистрация и вход по логину и паролю, cookie-сессии и изоляция данных по
  аккаунтам;
- создание, просмотр, повторное сохранение и удаление карточек турниров;
- автоматический расчёт раскладки фишек, уровней блайндов, банка и рекомендуемых
  призовых;
- учёт участников, ребаев, оплат и фактических выплат;
- режим общего банка и P2P-режим с расчётом переводов между игроками;
- реестр игроков с поиском, переименованием и мягким удалением профилей;
- защищённый лидерборд игроков по завершённым турнирам с количеством игр,
  суммой взносов, призами и чистой прибылью.

Buy-in задаётся при создании турнира и не меняется при последующих сохранениях.
Каждый ребай учитывается по цене buy-in. Отметки оплаты не изменяют расчётный
банк. Турнир считается завершённым для статистики, когда в карточке есть
результаты; сумма фактических выплат должна совпадать с банком.

## Архитектура

Приложение построено как модульный монолит:

1. `internal/transport/http` принимает HTTP-запросы через `chi`, проверяет
   сессию и преобразует JSON-модели.
2. `internal/service` реализует сценарии приложения и границы доступа к данным.
3. `internal/domain` содержит правила турнира и расчёты фишек, блайндов,
   призовых и переводов.
4. `internal/storage/postgres` хранит аккаунты, игроков и турниры через `pgx`.
5. `internal/storage/redis` хранит серверные сессии.

JSONB-карточка турнира остаётся источником истины для его редактируемого
содержимого. SQL-поля используются для владельца, поиска и связей. При
сохранении карточки транзакционно обновляется `tournament_players` — проекция
участников и финансовых показателей, из которой строится лидерборд. Запросы к
турнирам, игрокам и статистике ограничиваются аккаунтом из текущей сессии.

## Стек

| Компонент | Использование |
| --- | --- |
| Go 1.25 | backend и доменная логика |
| chi v5 | HTTP-маршрутизация и middleware |
| PostgreSQL | аккаунты, реестр игроков, связи и JSONB-карточки турниров |
| pgx v5 | доступ к PostgreSQL и транзакции |
| Redis | хранение сессий |

## Быстрый локальный запуск

Требуются Go 1.25, Docker Compose и `golang-migrate`.

```sh
cp -n .env.example .env
docker compose up -d --wait
make migrate-up
make run
```

Перед применением миграций необходимо проверить, что `DATABASE_URL` указывает
на отдельную локальную базу, а не на рабочую БД или облачный экземпляр.
Существующий `.env` команда `cp -n` не перезаписывает.

По умолчанию Compose публикует PostgreSQL на `127.0.0.1:5433`, Redis на
`127.0.0.1:6380`, а API запускается на `http://localhost:8080`. Проверка
доступности сервера: `GET /health`.

```sh
docker compose down
```

Данные PostgreSQL и Redis сохраняются в Docker volumes; обычный
`docker compose down` их не удаляет. Миграции при старте сервера автоматически
не выполняются.

## Конфигурация

Локальные значения без рабочих секретов приведены в `.env.example`. Файл
`.env` не должен попадать в Git.

| Переменная | Назначение и значение по умолчанию |
| --- | --- |
| `DATABASE_URL` | обязательная строка подключения к PostgreSQL |
| `REDIS_URL` | обязательная строка подключения к Redis; удалённый сервер требует `rediss://` с проверкой TLS |
| `PORT` | HTTP-порт, по умолчанию `8080` |
| `AUTH_COOKIE_SECURE` | `true` по умолчанию; для локального HTTP в примере используется `false` |
| `AUTH_SESSION_LIFETIME` | срок сессии, по умолчанию `720h`, допустимо от `1s` до `720h` |
| `HTTP_RATE_LIMIT_REQUESTS_PER_MINUTE` | скорость общего лимита на IP, по умолчанию `120` |
| `HTTP_RATE_LIMIT_BURST` | burst общего лимита, по умолчанию `60` |
| `AUTH_REGISTER_REQUESTS_PER_MINUTE` | скорость лимита регистрации, по умолчанию `5` |
| `AUTH_REGISTER_BURST` | burst лимита регистрации, по умолчанию `3` |
| `AUTH_LOGIN_REQUESTS_PER_MINUTE` | скорость лимита входа, по умолчанию `10` |
| `AUTH_LOGIN_BURST` | burst лимита входа, по умолчанию `10` |
| `HTTP_RATE_LIMIT_MAX_CLIENTS` | максимум IP-записей в памяти, по умолчанию `10000` |
| `HTTP_RATE_LIMIT_IDLE` | время неактивности IP-записи, по умолчанию `10m` |
| `HTTP_RATE_LIMIT_CLEANUP_INTERVAL` | интервал очистки IP-записей, по умолчанию `1m` |
| `AUTH_MAX_CONCURRENT_REQUESTS` | максимум параллельных операций входа и регистрации, по умолчанию `2` |
| `TEST_DATABASE_URL` | отдельная PostgreSQL БД для интеграционных тестов |
| `TEST_REDIS_URL` | отдельный локальный Redis для интеграционных тестов |

Пустые необязательные настройки используют значения по умолчанию. Невалидные
числа, длительности, URL или небезопасный удалённый Redis останавливают запуск.

## API

Прикладные ручки используют JSON, а `GET /health` отвечает `text/plain`.
Получение аккаунта и работа с игроками, турнирами и статистикой требуют
cookie-сессию. Проверка состояния, регистрация и вход доступны без неё;
logout без cookie также возвращает `204`. Защищённые ответы получают
`Cache-Control: no-store`.

### Авторизация

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/auth/register` | создать аккаунт |
| `POST` | `/auth/login` | создать сессию и установить cookie |
| `POST` | `/auth/logout` | завершить текущую сессию |
| `GET` | `/auth/me` | получить текущий аккаунт |

Регистрация и вход принимают `login` и `password`. Логин содержит 3–32 символа
из латинских букв, цифр, `_`, `-`, `.`, нормализуется в нижний регистр и
уникален без учёта регистра. Пароль содержит 8–128 печатных ASCII-символов без
пробелов и хранится только как Argon2id-хэш со случайной солью. Регистрация не
создаёт сессию автоматически.

### Игроки

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/players` | создать профиль игрока |
| `GET` | `/players?q=вл&limit=50&offset=0` | найти активных игроков |
| `PATCH` | `/players/{player_id}` | переименовать игрока |
| `DELETE` | `/players/{player_id}` | мягко удалить игрока из активного реестра |

Имена нормализуются по пробелам и регистру для проверки уникальности внутри
аккаунта, но сохраняют отображаемый регистр. Удалённый профиль остаётся в
истории турниров и не возвращается в списке активных игроков.

### Турниры

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/tournaments` | создать турнир |
| `GET` | `/tournaments?limit=50&offset=0` | получить список турниров |
| `GET` | `/tournaments/{id}` | получить карточку турнира |
| `PUT` | `/tournaments/{id}` | полностью сохранить редактируемую карточку |
| `PATCH` | `/tournaments/{id}/players/{player_id}` | изменить оплаты и ребаи участника |
| `DELETE` | `/tournaments/{id}` | удалить турнир |

### Статистика

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/statistics/leaderboard?limit=50&offset=0` | получить лидерборд текущего аккаунта |

Ручка защищена cookie-сессией. `limit` по умолчанию равен `50` и допускает
значения от `1` до `100`; `offset` по умолчанию равен `0`. Ответ содержит
`player_id`, `name`, `tournaments_played`, `total_buy_ins`, `total_prizes` и
`net_profit`. Учитываются все участники турниров с непустыми результатами;
удалённые профили в лидерборде не показываются.

## Данные и миграции

Миграции находятся в `migrations/` и применяются отдельно от запуска сервера:

| Миграция | Изменение |
| --- | --- |
| `000001` | таблица JSONB-карточек турниров |
| `000002` | удаление устаревшего статуса турнира |
| `000003` | аккаунты и обязательный владелец турнира |
| `000004` | реестр игроков и связи участников с турнирами |
| `000005` | `contribution`, `prize` и `included_in_statistics` в проекции участников |

`000003` рассчитана на новую пустую базу: существующим турнирам владелец
автоматически не назначается. `000004` не переносит старые карточки со
случайными ID участников. `000005` не выполняет backfill статистики из JSONB:
существующие строки получают нулевые значения и не включаются в статистику до
повторного сохранения карточки.

## Тестирование

Unit-тесты и проверки без интеграционных подключений:

```sh
make test-unit
go vet ./...
go build ./...
```

Интеграционные тесты запускаются только с отдельными тестовыми сервисами:

```sh
make migrate-test-up
make test-storage
```

`TEST_DATABASE_URL` должен указывать на отдельную PostgreSQL БД, имя которой
заканчивается на `_test`, с применёнными миграциями. Интеграционные тесты
очищают тестовые таблицы, поэтому рабочая локальная БД и облачная БД для них не
подходят. `TEST_REDIS_URL` допускает только отдельный Redis на loopback-адресе;
рабочий Redis использовать нельзя. Без этих переменных интеграционные тесты в
обычном unit-запуске пропускаются.

## Известные ограничения

- frontend отсутствует;
- полный `PUT` карточки не использует версионирование и может перезаписать
  более свежие изменения другого клиента; точечный `PATCH` оплат и ребаев
  выполняется с транзакцией и блокировкой строки;
- лидерборд показывает только общую статистику за всё время: без периодов,
  ROI, мест и отдельной страницы игрока;
- для старых данных нет автоматического backfill статистической проекции;
- миграции, резервное копирование и эксплуатационная конфигурация остаются
  ответственностью окружения;
- rate limit хранится в памяти одного процесса и определяет клиента по
  `RemoteAddr`; конфигурация за прокси требует отдельной проверки;
- успешная сборка и прохождение тестов сами по себе не означают готовность к
  production-эксплуатации.
