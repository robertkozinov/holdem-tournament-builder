# Holdem Tournament Builder

Backend для домашних офлайн-турниров по техасскому холдему.

Приложение рассчитывает раскладку фишек, структуру блайндов и рекомендации
призовых. Организатор сохраняет участников, ребаи и фактические выплаты.
Карточку можно открыть и исправить в любой момент. Есть режим банка с
отметками оплат и режим P2P с расчётом переводов.

Go, PostgreSQL, JSONB, chi, pgx, Redis. Авторизация по логину и паролю,
данные турниров и реестры игроков изолированы по аккаунтам. Frontend пока нет.

## Запуск

Нужны Go 1.25+, Docker Compose и golang-migrate. Можно использовать свои
PostgreSQL и Redis вместо контейнеров.

Для локального запуска на новой БД:

Если `.env` уже существует, сначала сверь адреса PostgreSQL и Redis
с `.env.example`. Не запускай миграции, пока не убедишься, что выбрана
новая локальная БД, а не рабочая база или Neon.

```sh
cp -n .env.example .env
docker compose up -d --wait
make migrate-up
make run
```

`compose.yaml` поднимает PostgreSQL на `127.0.0.1:5433` и Redis на
`127.0.0.1:6380`. Порты и локальные параметры уже указаны в `.env.example`.
Файл `.env` не попадает в Git. Не перезаписывай существующий `.env` с
настройками другой БД. Контейнеры сохраняют данные в Docker volumes;
`docker compose down` их не удаляет.

API: `http://localhost:8080`. Публичная проверка сервера: `GET /health`.
Для остановки локальных зависимостей: `docker compose down`.

Миграция `000003` добавляет аккаунты и обязательного владельца турнира.
Она не удаляет и не присваивает существующие турниры: на непустой старой
таблице без владельцев завершится ошибкой с откатом всей миграции.
Для этой версии используй отдельную пустую БД. Применение миграций к
рабочей базе и перенос старых данных требуют отдельного решения.

Миграция `000004` добавляет реестр и связи участников с турнирами.
Переноса карточек со старыми случайными ID участников нет: эта версия
рассчитана на новые турниры. Миграции автоматически при запуске не выполняются.

## Авторизация

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/auth/register` | Создание аккаунта, `201` |
| POST | `/auth/login` | Вход и session cookie, `200` |
| POST | `/auth/logout` | Завершение текущей сессии, `204` |
| GET | `/auth/me` | Текущий аккаунт, `200` |

Регистрация и вход принимают JSON с полями `login` и `password`.
В ответе только `id` и `login`, без пароля, хэша и токена.
Регистрация не выполняет автоматический вход.

Логин: 3–32 символа, латиница, цифры, `_`, `-`, `.`. Пробелы по краям
удаляются, регистр не учитывается. Пароль: 8–128 ASCII-символов без
пробелов, обязательных сочетаний букв, цифр и спецсимволов нет.
Пароль хранится как Argon2id-хэш со случайной солью.

Сессия действует 30 дней от входа без продления при чтении. В cookie
передаётся случайный токен, в Redis хранится запись под его SHA-256-хэшем
с TTL. Выход завершает только текущую сессию. Другие устройства остаются
авторизованными; потеря данных Redis потребует повторного входа.

Все операции `/tournaments`, `/players` и `/auth/me` требуют cookie. Чужой турнир
возвращает `404`, отсутствующая или истёкшая сессия — `401`, недоступный
Redis — `503`. Есть защита unsafe-запросов от cross-origin браузерных
запросов, ограничения частоты запросов и параллельной обработки входа
и регистрации.
UI и API должны работать на одном origin; открытый CORS не включён.

## Реестр игроков

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/players` | Создать игрока по `{"name":"Влад"}`, `201` |
| GET | `/players?q=вл&limit=50&offset=0` | Список активных игроков, поиск по подстроке |
| PATCH | `/players/{player_id}` | Переименовать по `{"name":"Влад Фед"}` |
| DELETE | `/players/{player_id}` | Удалить из активного реестра, `204` |

Имена от 1 до 100 символов; лишние пробелы убираются, регистр отображения
сохраняется. `Влад`, `влад` и `ВЛАД` считаются одним активным именем
внутри аккаунта. Дубликат при отдельном создании или переименовании — `409`.
Поиск `%` и `_` буквальный, без SQL-масок. Ответ игрока: `id`, `name`, `is_deleted`.

В `players` запроса турнира можно передать `{"id":"UUID"}` для выбора
существующего игрока или `{"name":"Влад"}`. Полное нормализованное совпадение
переиспользует профиль, иначе профиль создаётся вместе с карточкой в одной
транзакции. Частичное совпадение ничего не выбирает автоматически.
Если указан ID, присланное имя не меняет профиль: переименование выполняется
только через `/players/{player_id}`.

UUID сохраняется при переименовании, актуальное имя показывается во всех
карточках и результатах. Удалённый игрок остаётся в своих турнирах с последним
именем и `is_deleted=true`; оплаты, ребаи и выплаты не меняются. Его нельзя
добавить в новый турнир или переименовать. Новое создание того же имени выдаёт
другой UUID и не связывает историю. P2P считает по UUID, даже если имена совпали;
в ответах переводов есть `from_player_id`, `to_player_id` и отображаемые `from`, `to`.

Полный PUT заменяет карточку и пока не обнаруживает устаревшую версию клиента.
Транзакция не устраняет этот риск; для оплат и ребаев используется PATCH.
API статистики и новый UI не входят в этот этап.

## Конфигурация

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Обязательная строка PostgreSQL |
| `REDIS_URL` | Обязательная строка Redis; для удалённого сервера нужен `rediss://` |
| `PORT` | HTTP-порт, по умолчанию `8080` |
| `AUTH_COOKIE_SECURE` | По умолчанию `true`; `false` только для локального HTTP |
| `AUTH_SESSION_LIFETIME` | По умолчанию `720h`, допустимо от `1s` до `720h` |
| `HTTP_RATE_LIMIT_REQUESTS_PER_MINUTE` | Скорость пополнения общего лимита на IP, по умолчанию `120` |
| `HTTP_RATE_LIMIT_BURST` | Максимальный запас общего лимита, по умолчанию `60` |
| `AUTH_REGISTER_REQUESTS_PER_MINUTE` | Скорость пополнения лимита регистрации на IP, по умолчанию `5` |
| `AUTH_REGISTER_BURST` | Максимальный запас лимита регистрации, по умолчанию `3` |
| `AUTH_LOGIN_REQUESTS_PER_MINUTE` | Скорость пополнения лимита входа на IP, по умолчанию `10` |
| `AUTH_LOGIN_BURST` | Максимальный запас лимита входа, по умолчанию `10` |
| `HTTP_RATE_LIMIT_MAX_CLIENTS` | Максимум записей IP в памяти, по умолчанию `10000` |
| `HTTP_RATE_LIMIT_IDLE` | Срок без запросов до удаления записи IP, по умолчанию `10m` |
| `HTTP_RATE_LIMIT_CLEANUP_INTERVAL` | Интервал проверок устаревших записей IP, по умолчанию `1m` |
| `AUTH_MAX_CONCURRENT_REQUESTS` | Общий предел параллельных запросов входа и регистрации, по умолчанию `2` |

Настройки защиты запросов принимают положительные целые числа и
положительные длительности (`30s`, `5m`). Пустые переменные оставляют
дефолты; невалидные значения останавливают запуск с указанием переменной.
Настройки читаются при запуске: после изменения окружения нужен перезапуск.

`REQUESTS_PER_MINUTE` задаёт скорость восстановления разрешений, а не
строгую квоту за календарную минуту. `BURST` позволяет короткую серию
запросов за счёт накопленного запаса. Вход и регистрация проходят как общий,
так и свой отдельный лимит. Превышение частоты возвращает `429` с
`Retry-After`, занятые auth-слоты возвращают `503` без постановки в очередь.
Число слотов не ограничивает количество уже авторизованных пользователей.

Счётчики и auth-слоты локальны для одного процесса и сбрасываются при
перезапуске. Очистка записей IP выполняется приходящими запросами, не
отдельным таймером. IP берётся из `RemoteAddr`, без доверия к произвольному
`X-Forwarded-For`; перед размещением за прокси нужно проверить адрес клиента.

При HTTPS cookie называется `__Host-holdem_session`, локально при
`AUTH_COOKIE_SECURE=false` — `holdem_session`. В обоих случаях используются
HttpOnly, SameSite=Lax и Path=/, без Domain.

Для Render укажи PostgreSQL URL из Neon и TLS Redis URL из Upstash в
секретах сервиса, оставь `AUTH_COOKIE_SECURE=true`. Сервер использует
предоставленный Render `PORT`. Код не создаёт облачные ресурсы и не
запускает миграции автоматически. Без Redis сервер не стартует.
На бесплатном Redis учитывай квоту: каждый защищённый запрос читает
сессию; частый polling будет расходовать лимит команд.

## Проверки

```sh
make test-unit
go vet ./...
go build ./...
```

Интеграционные тесты включаются через `TEST_DATABASE_URL` и
`TEST_REDIS_URL`; после их настройки запускай `make test-storage`.
PostgreSQL должен быть отдельной тестовой БД с именем, заканчивающимся
на `_test`, и применёнными миграциями. Тесты проверяют фактическое имя БД,
затем очищают `tournament_players`, `tournaments`, `players` и создают
тестовые аккаунты.
Redis допускается только на loopback-адресе в отдельном тестовом
экземпляре; удаляются только созданные тестами ключи, без `FLUSHDB`.
Не используй Neon, рабочую БД или Upstash для этих проверок.
Без соответствующих переменных интеграционные проверки пропускаются.
